# 02 工作约束

- 版本：v0.1（P0 草案）
- 状态：待确认
- 日期：2026-11-15
- 关联：[需求与范围](00-需求与范围.md) / [架构设计](01-架构设计.md) / [阶段计划](03-阶段计划.md)

> 本文是「先约束行为，再允许实现」的规则文件。任何阶段开始前，双方以本文为准。

## 1. 总则

1. **设计先行**：每个阶段先提交《阶段设计说明》，经你确认后才允许写代码。
2. **一次一阶段**：同一时间只推进一个阶段；上一阶段未验收，不开始下一阶段。
3. **范围锁定**：阶段内不新增需求；发现新需求记入 backlog，下阶段评估。
4. **可回滚**：每阶段结束打 Git tag；失败可整体回退。
5. **安全优先**：任何便利性设计不得突破“秘密不泄露、默认不暴露、写操作有确认”三条底线。

## 2. 阶段流程（五步门禁）

```
① 写设计（docs/phases/Pn-*.md）
      ↓ 你确认
② 确认（明确回复「确认 Pn 设计，可开工」）
      ↓
③ 编码（仅本阶段范围）
      ↓
④ 验证（build 0 warning + test 全绿 + 手工演示）
      ↓
⑤ 验收（你确认；打 tag pn-done；更新文档；进入下一阶段设计）
```

未完成第 ④ 步不得进入第 ⑤ 步；未完成第 ⑤ 步不得开始下一阶段。

## 3. 阶段设计说明模板（必填）

每个 `docs/phases/Pn-*.md` 必须包含：

1. 目标 / 非目标；
2. 页面与交互（线框或文字描述）；
3. 接口与端点（HTTP 方法、路径、请求/响应模型）；
4. 类与接口签名（关键类型，不含实现）；
5. 数据模型与迁移（表、字段、索引）；
6. 错误矩阵（场景 → 用户可见提示 → 日志级别）；
7. 配置项（名称、默认值、是否必填、环境变量映射）；
8. 测试清单（用例编号 + 断言点）；
9. 验收步骤（可复现的手工步骤）；
10. 风险与未决问题。

## 4. 编码规范

- 目标框架 `net10.0`；`Nullable=enable`；`ImplicitUsings=enable`；`LangVersion=latest`。
- 分析器全开：`AnalysisLevel=latest`、`TreatWarningsAsErrors=true`；不得用 `#pragma warning disable` 绕过，确需例外须在设计文档说明。
- 全异步：I/O 一律 `async` + `CancellationToken`；禁止 `.Result`、`.Wait()`、`Task.Run` 包裹同步 I/O。
- 命名与结构：file-scoped namespace；一个文件一个公开类型；接口 `I` 前缀；异步方法 `Async` 后缀。
- 依赖注入：构造函数注入；禁止 service locator；`IOptions<T>` + 启动校验（`ValidateOnStart`）。
- JSON：全项目统一一个 `JsonSerializerOptions`（`PropertyNameCaseInsensitive=true`，忽略未知字段），禁止散落自定义。
- 日志：结构化参数，禁止字符串拼接敏感值；`ApiKey`、`Token`、`Authorization`、`Cookie` 必须脱敏。
- 时间：统一 UTC 存储与计算；展示层转本地时区（Asia/Shanghai）。
- 禁止硬编码节点地址、密钥、生产 URL；全部走配置。
- 注释：公共类型/关键算法写 XML 注释；不写“翻译代码”的废话注释。

## 5. 架构约束

1. Blazor 页面不得直接 `new HttpClient` 或拼 1Panel URL，只能调用 Application 层服务。
2. 1Panel 访问只能通过 `IPanelClient` 及其域客户端；禁止在 UI/Application 里手写 HTTP 调用。
3. 节点 API Key 只在 Infrastructure 的密钥服务中解密，且只在签名处理器内短暂使用；禁止进入领域对象、日志、异常消息。
4. 1Panel 路由路径只在 `PanelRoutes` 一处定义；新增路径必须同时补契约测试。
5. 对外错误统一为 `PanelError`；禁止把 `HttpRequestException`、`JsonException` 直接抛给页面。
6. 新增项目/分层调整必须先写 ADR 并经确认。

## 6. 依赖与包管理

- **项目创建统一用 `dotnet new`；包引用统一用 `dotnet add package`；项目引用统一用 `dotnet add reference`。**
- `dotnet add package` 不指定版本，由 NuGet 解析最新兼容版本；禁止手写或猜测 `PackageReference Version`。确需固定版本时，先在阶段设计文档说明，再用 `--version` 显式添加。
- `FrameworkReference` 等非包引用没有 CLI 添加命令，允许在 csproj 中显式维护，但必须在阶段文档记录原因（P1：ContractTests 需要 `Microsoft.AspNetCore.App` 运行进程内 Kestrel）。
- 新增 NuGet 包必须在阶段设计文档的「依赖变更」一节列明：包名、解析出的版本、用途、许可证、替代方案。
- 优先使用 BCL 与 ASP.NET Core 内置能力；能不引包就不引包。
- 禁止引入需要商业授权或来源不明的包。

## 7. 测试门槛

- 每个阶段结束时 `dotnet test` 全绿；新增逻辑必须有对应用例。
- 鉴权、签名、错误映射、合并排序、缓存降级属于**必须覆盖**清单。
- 契约测试使用进程内假 1Panel，不依赖真实面板；真实面板冒烟测试通过环境变量显式开启，默认跳过。
- Bug 修复必须先写失败用例，再修复。
- P3 起要求 Client 核心逻辑行覆盖率 ≥ 70%（coverlet），未达标需在设计文档说明原因。

## 8. Git 工作流

- 本机已安装 **Git 2.56.1**（`C:\Program Files\Git\cmd\git.exe`）；仓库根目录 `D:\文件\子目录`，默认分支 `main`。
- **每次迭代至少一次提交并打 tag**（`p0-done`、`p1-done`……）；需要并行/试验时分叉特性分支，合并前跑全量构建与测试。
- 每阶段一个或多个提交，提交信息格式：
  - `docs(p0): ...` / `feat(p1): ...` / `test(p1): ...` / `fix(p1): ...` / `chore(p1): ...`
- 每阶段验收后打 tag：`p0-done`、`p1-done`……
- `.gitignore` 必含：`bin/`、`obj/`、`tools/`、`data/`、`logs/`、`*.db`、`appsettings.Local.json`、`secrets/`。
- 禁止提交任何真实 API Key、OIDC secret、节点地址清单。

## 9. 安全红线（不可协商）

1. 默认只监听 `127.0.0.1`；对外监听必须显式配置。
2. 不允许本地账号密码登录；只允许 OIDC + 白名单，白名单为空时拒绝启动。
3. API Key、OIDC secret、Cookie 不得出现在日志、异常、审计详情、页面、API 响应中。
4. 节点 TLS 校验默认严格；允许自签必须逐节点显式开启并在 UI 提示风险。
5. 写操作（首版没有）与敏感读取必须审计。
6. 任何“调试开关”必须仅在 Development 环境生效，并在启动日志中明确告警。

## 10. 完成定义（DoD）

一个阶段完成 = 以下全部满足：

- [ ] 设计文档与实际实现一致（不一致处已更新文档）；
- [ ] `dotnet build -c Release` 0 warning；
- [ ] `dotnet test -c Release` 全绿；
- [ ] 本阶段验收步骤可复现通过；
- [ ] 新增/修改的配置项在文档中列出；
- [ ] 无密钥、数据文件、构建产物被提交；
- [ ] 审计与日志行为符合安全红线；
- [ ] 打 tag 并更新阶段计划状态。

## 11. 变更控制

- 任何偏离 [架构设计](01-架构设计.md) 的决定，先写 `docs/adr/ADR-XXXX-标题.md`（背景、选项、决定、后果），经你确认后实施。
- 需求变更：记入 `docs/backlog.md`，当前阶段不做。
- 发现设计缺陷：立即暂停编码，更新设计文档并重新确认，不带病推进。

## 12. 汇报节奏

- **设计对齐**：阶段开始，提交设计说明，等你确认。
- **验收演示**：阶段结束，给出构建/测试结果、运行命令、验收步骤与已知问题。
- 期间不频繁打断；遇到必须你决策的问题立即提出。

## 13. 禁止事项

- 未经确认开始编码；
- 在未确认的情况下扩大范围或改接口；
- 跳过测试、注释掉测试、伪造测试通过；
- 在代码/配置/文档中写入真实密钥或生产地址；
- 引入未列明的依赖；
- 大规模无关重构（与当前阶段无关）；
- 直接删除或破坏节点数据、审计数据。
