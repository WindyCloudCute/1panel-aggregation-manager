- 关联：[需求与范围](00-需求与范围.md) / [架构设计](01-架构设计.md) / [工作约束](02-工作约束.md) / [阶段计划](03-阶段计划.md) / [P3 聚合总览详细设计](06-P3-聚合总览详细设计.md)

## 1. 目标与非目标

**目标**：在一个页面里按类型查看所有节点的五类只读资源，支持跨节点合并、过滤、排序、分页、单节点/全量刷新与详情。

1. 五类资源：**网站、应用（已安装）、容器、数据库、计划任务**；
2. 跨节点合并：同一张表里展示「节点 + 资源」；节点失败时其余节点照常显示（部分失败可见）；
3. 过滤/排序/分页在**合并后**做，保证跨节点结果一致；
4. 复用 P3 的并发/超时/预算/熔断能力，不重复造轮子；
5. 每节点每类资源有**条数上限**，超出明确提示；
6. 详情：按需加载，只读，不阻塞列表；
7. 缓存 + TTL + 手动刷新；**P4 不做实时推送**（列表场景不需要秒级更新）。

**非目标**：

- 写操作（启动/停止/删除/升级/改配置）；
- 历史/趋势、告警、导出（P5+）；
- 计划任务执行记录、容器日志/终端、文件管理（后续阶段）；
- 独立的 SignalR 实时推送（P4 列表用 TTL 缓存 + 手动刷新；如需要再加）；
- 跨节点依赖关系图、拓扑。

## 2. 数据来源与真实契约

> 真实探测见 `docs/research/p4-api-probe.md`（2026-11-16 对 1Panel v2.3.2 实测）；路由/DTO/源码依据见 `docs/research/p4-api-routes.md`（官方 tag v2.3.2 源码 + Swagger + 前端接口，含 `order` 合法值 `ascending/descending` 与各资源 `orderBy` 枚举）。

### 2.1 列表接口汇总

| 资源 | 列表接口 | 请求体 | 每项关键字段（展示用） |
|---|---|---|---|
| 网站 | `POST /api/v2/websites/search` | `{page,pageSize,name,orderBy,order,websiteGroupId}`；`orderBy/order` 必填 | `id, primaryDomain, alias, type, status, expireDate, sitePath, appName, runtimeName` |
| 应用 | `POST /api/v2/apps/installed/search` | `{page,pageSize,type?,unused?,all?}` | `id, name, version, status, message, httpPort, httpsPort, path, appKey, appType` |
| 容器 | `POST /api/v2/containers/search` | `{page,pageSize,name,state,filters,orderBy,order}`；`state/orderBy/order` 必填 | `containerID, name, imageName, state, runTime, ports[], isFromApp, isFromCompose, appName, description` |
| 数据库 | 实例：`GET /databases/db/list/{type}`；库：`POST /databases/search`（MySQL）/`/databases/pg/search`/`/databases/mongodb/search` | 实例列表无 body；库列表 `{page,pageSize,database:<实例名>,orderBy,order}` | MySQL：`id,name,mysqlName,from,format,collation,description`；PG：`name,postgresqlName,format,superUser`；Mongo：`name,mongodbName` |
| 计划任务 | `POST /api/v2/cronjobs/search` | `{page,pageSize,info,groupIDs,orderBy,order}` | `id, name, type, spec/specs, status, executor, command/script, appID, website, dbName, retainCopies` |

### 2.2 详情接口

| 资源 | 详情接口 | 说明 |
|---|---|---|
| 网站 | `GET /api/v2/websites/{id}` | 返回完整 `WebsiteDTO`（域名/SSL/运行环境等） |
| 应用 | `GET /api/v2/apps/installed/info/{id}` | `id,name,version,status,message,HttpPort,container,composePath,appKey,env` |
| 容器 | `POST /api/v2/containers/info` body `{name}` | `ContainerHelper`（镜像/网络/端口/env/资源限制）；`/containers/inspect` 需 `{id,type}`，P4 不用 |
| 数据库 | 无独立详情接口 | 列表字段已足够；详情面板展示列表属性 |
| 计划任务 | `POST /api/v2/cronjobs/load/info` body `{id}` | `CronjobOperate` 完整字段 |

### 2.3 数据库的两层结构（关键约束）

1Panel v2 的数据库是「**实例**（MySQL/PostgreSQL/MongoDB）→ **库**」：

- 实例列表：`GET /databases/db/list/mysql`、`/postgresql`、`/mongodb`，返回 `DatabaseOption[]`（`database` 是实例名，如 `MySQL`）；
- 库列表：需要把实例名作为 `database` 参数传给对应引擎的 `/search`；
- 实测：真实节点 MySQL 实例 1 个（`MySQL`，远程 198.51.100.11），库 5 个；PG/Mongo 实例为 `null`；
- 因此「每节点 1 次列表调用」对数据库**不成立**：一次采集 = 3 次实例列表 + Σ(每实例 1 次库列表)。实例通常 1~3 个，可接受。

### 2.4 兼容与容错

- 空列表：`data.items` 为 `null` 或 `[]`，DTO 必须容忍；
- 排序参数：不同版本对 `orderBy` 的合法值不同（如网站 `created_at`、容器 `name/state`、计划任务 `name/status/createdAt`、数据库 `name`）；实现用已验证值，若返回 400 校验错误则**回退为无排序/默认排序**并记录 warning，不判为节点失败；
- 容器 `ports`/`network` 结构不稳定，展示时统一转字符串；
- 详情接口 404/500：详情面板显示可操作错误，不影响列表。

## 3. 领域模型

> 位于 `PanelFleet.Application/Models/ResourceModels.cs`；不可变 record；不依赖 EF/ASP.NET。

```csharp
public enum ResourceKind
{
    Websites = 0,
    Apps = 1,
    Containers = 2,
    Databases = 3,
    Cronjobs = 4
}

public enum ResourceNodeState
{
    Success = 0,     // 全部成功
    Partial = 1,     // 部分引擎/分页失败，但有数据
    Failed = 2,      // 无数据且失败
    Skipped = 3,     // 节点禁用
    Pending = 4      // 尚未采集
}

/// <summary>合并后的一行：节点 + 资源。</summary>
public sealed record ResourceRow(
    NodeId NodeId,
    string NodeName,
    ResourceKind Kind,
    string SourceId,                                  // 各资源自己的 id（网站 id、容器 ID、库 id 等）
    string Name,
    string? Status,
    IReadOnlyDictionary<string, string?> Attributes); // 各类型展示字段（键见 §4.3）

/// <summary>单节点单类资源的采集结果（缓存单位）。</summary>
public sealed record NodeResourceResult(
    NodeId NodeId,
    string NodeName,
    ResourceKind Kind,
    ResourceNodeState State,
    IReadOnlyList<ResourceRow> Rows,
    int Total,                    // 1Panel 报告的 total（可能大于 Rows.Count）
    bool Truncated,               // 超过每节点上限
    IReadOnlyList<string> Warnings,
    PanelError? Error,
    DateTimeOffset? FetchedAt,
    DateTimeOffset? AttemptedAt,
    TimeSpan Elapsed);

/// <summary>列表页响应。</summary>
public sealed record ResourcePage(
    ResourceKind Kind,
    DateTimeOffset GeneratedAt,
    IReadOnlyList<ResourceRow> Rows,
    int TotalMatched,             // 过滤后的总数（合并后）
    int Page,
    int PageSize,
    int TotalPages,
    int NodesSucceeded,
    int NodesFailed,
    int NodesTotal,
    IReadOnlyList<NodeResourceResult> Nodes);

/// <summary>详情（按需加载）。</summary>
public sealed record ResourceDetail(
    NodeId NodeId,
    string NodeName,
    ResourceKind Kind,
    string SourceId,
    string Name,
    IReadOnlyDictionary<string, string?> Fields,
    DateTimeOffset FetchedAt,
    PanelError? Error);

public sealed record ResourceQuery(
    string? Filter,
    string? Sort,                 // name | status | node | 类型特定键
    bool Descending,
    int Page,
    int PageSize,
    bool ForceRefresh);
```

## 4. 采集

### 4.1 复用 P3 的 FanoutEngine

- 每个「节点 × 资源类」是一个 `FanoutTarget`，按 `Resources:MaxConcurrency` 并发；
- 单节点超时 `Resources:NodeTimeoutSeconds`（默认 10s；数据库多层调用也在此预算内）；
- 整类刷新整轮预算 `Resources:BudgetSeconds`（默认 15s）；
- 结果流式返回，页面先显示快节点，慢节点后到（复用 P3 的增量渲染思路，但 P4 不做跨请求推送；当前请求内完成合并后返回）。

### 4.2 每类资源的采集步骤

**网站 / 应用 / 容器 / 计划任务**：每节点 1 次列表调用（`pageSize=PerNodeLimit`），映射为 `ResourceRow`。

**数据库**（`DatabaseResourceLoader`）：

1. 依次（可并发 3 个）`GET /databases/db/list/mysql|postgresql|mongodb`；
2. 对每个返回的实例，调用对应引擎的 `/search`（`pageSize=PerNodeLimit`，`database=实例名`）；
3. 合并为 `Rows`，`Attributes` 带 `engine`、`instance`、`format/collation`、`address` 等；
4. 某引擎接口 404/未安装（`data:null`）→ 视为空，不报错；某引擎失败但其它成功 → `Partial` + `Warnings`；全部失败 → `Failed`。

### 4.3 各类型展示字段（Attributes 键）

| 类型 | Attributes 键（左侧为表格列，详情面板用全部） |
|---|---|
| 网站 | `primaryDomain, alias, type, expireDate, sitePath, appName, runtimeName` |
| 应用 | `version, appKey, appType, httpPort, httpsPort, path, message` |
| 容器 | `image, runTime, ports, source`（`source` = 应用/Compose/手动）, `appName` |
| 数据库 | `engine, instance, format, collation, address, description` |
| 计划任务 | `type, spec, executor, command, website, appID, dbName, retainCopies` |

- 值为 `string?`；缺失字段不写或写 null；
- 时间字段统一 ISO-8601，展示层本地化；
- 敏感字段（数据库密码等响应里有但为空/不允许展示）**不映射**。

### 4.4 每节点上限与合并上限

- `Resources:PerNodeLimit`（默认 200）：每节点每类最多取 200 条；`Total > Rows.Count` 时 `Truncated=true`；
- `Resources:MergeLimit`（默认 2000）：合并后最多保留 2000 行，超出截断并提示「结果过多，请用搜索/节点筛选缩小范围」；
- UI 明确显示「该节点共 N 条，当前仅展示前 200 条」。

### 4.5 失败与降级

| 情况 | NodeResourceResult |
|---|---|
| 全部成功 | `Success` |
| 部分成功（数据库多引擎） | `Partial` + Warnings |
| 401/403 | `Failed`，错误原文（鉴权类） |
| 网络/TLS/超时 | `Failed`，保留该节点上次缓存（若存在）并标 Stale |
| 预算耗尽 | `Failed`（BudgetExceeded 错误），不算该节点故障（与 P3 一致，不记熔断） |
| 节点禁用 | `Skipped`，不发请求 |
| 未采集过 | `Pending` |

- 列表页顶部显示「节点成功 x/y」与失败节点原因；表格只展示有数据的节点行；
- 缓存保留 + `IsStale` 标注（复用 P3 的 `AttemptedAt` CAS 语义）。

## 5. 缓存与刷新

### 5.1 缓存单位与 TTL

```csharp
public sealed record ResourceCacheEntry(NodeResourceResult Result);
public interface IResourceCache
{
    bool TryGet(NodeId nodeId, ResourceKind kind, DateTimeOffset now, out NodeResourceResult result, out bool isFresh);
    bool Apply(NodeResourceResult result);        // AttemptedAt CAS，旧结果不覆盖新结果
    void SetDetail(ResourceDetail detail);
    bool TryGetDetail(NodeId nodeId, ResourceKind kind, string sourceId, out ResourceDetail detail);
    void Prune(IReadOnlySet<NodeId> validNodeIds);
}
```

- 缓存键：`(NodeId, ResourceKind)`；TTL `Resources:CacheTtlSeconds`（默认 30s）；
- 详情缓存键：`(NodeId, ResourceKind, SourceId)`，TTL `Resources:DetailCacheTtlSeconds`（默认 60s）；
- 过期策略：**stale-while-revalidate 简化版**——查询时若缓存过期则同步重新采集（受节点超时/预算约束）；失败时保留旧数据并标 Stale；
- 同一 `(node,kind)` 的并发采集用 `SemaphoreSlim(1,1)` gate：已有请求在跑时，后来者直接使用缓存（可能 stale），避免重复打节点；
- 重启清空，无持久化。

### 5.2 刷新入口

- 页面「刷新」→ `RefreshAsync(kind)`：并发采集所有启用节点（受预算约束）；
- 表格节点筛选后「刷新此节点」→ `RefreshNodeAsync(kind, nodeId)`；
- 打开页面首次：`QueryAsync(kind, page=1)`，缓存为空则采集；过期则重新采集；
- **后台定时刷新**：`ResourceRefreshHost` 每 `Resources:RefreshIntervalSeconds`（默认 60s）刷新「最近被访问过」的资源类型（`Resources:AccessTtlSeconds` 默认 600s 内打开过），未访问过的类型不预热，控制 1Panel 负载；
- 页面每 10s 用 `CacheOnly` 模式重读缓存并重渲染（不触发网络），配合后台刷新实现「自动更新」；手动刷新仍走 `EnsureFresh`；
- 切 tab：各类型独立缓存，按需采集；
- 负载估算：访问过 5 类、10 节点 → 约每 60s 50 次列表请求（数据库再按实例数增加），可通过调大间隔或 `0` 禁用。

## 6. REST API

均 `Admin` 策略；`POST` 要求 `X-CSRF-TOKEN`（复用 P2 机制）。

| 方法 | 路径 | 说明 | 成功 | 错误 |
|---|---|---|---|---|
| GET | `/api/resources/{kind}` | 合并查询；query：`filter,sort,descending,page,pageSize` | 200 `ResourcePage` | 400/401/403 |
| POST | `/api/resources/{kind}/refresh` | 刷新全部启用节点（同步等待，受预算 15s） | 200 `ResourcePage` | 400/401/403 |
| POST | `/api/resources/{kind}/nodes/{id}/refresh` | 刷新单节点（同步等待，≤节点超时+2s） | 200 `ResourcePage` | 400/401/403/404 |
| GET | `/api/resources/{kind}/{nodeId}/{sourceId}` | 详情（按需） | 200 `ResourceDetail` | 400/401/403/404 |

- `kind` 取值：`websites|apps|containers|databases|cronjobs`（不区分大小写）；
- 页面（Blazor）直接调用 Application 服务，不经过 HTTP；REST 供测试/脚本/后续客户端；
- 同步等待是刻意选择（列表页需要立即拿到结果）；最坏等待 = 预算 15s。

## 8. 授权、审计与安全

- 全部页面与 API 要求 `Admin`（P2 现状）；只读，无新权限模型；
- 读操作**不写审计**；刷新写 Information 日志（kind/节点数/成功失败/耗时），单节点失败 Warning；
- 不返回数据库密码等敏感字段；详情接口返回内容在服务端裁剪（只保留展示字段）；
- 出站请求受并发/超时/预算限制；每节点每类一次采集，数据库按实例数增加；
- 详情「在 1Panel 中打开」使用节点 BaseUrl + 安全入口，新标签页 `noopener`。

- 启动时 fail-closed 校验（非法值直接启动失败，与 P3 一致，不做静默 clamp）。

## 14. 风险与待确认问题

| 风险/问题 | 影响 | 对策/待确认 |
|---|---|---|
| 1Panel 排序参数版本差异 | 400 校验失败 | 已验证值 + 失败回退默认排序；保留 warning |
| 数据库两层结构导致请求数增加 | 采集变慢 | 每节点 3 次实例列表 + 每实例 1 次库列表；默认超时 10s/预算 15s |
| 大节点数据量 | 页面/面板压力 | PerNodeLimit=200 + MergeLimit=2000 + 提示；可配置 |
| 详情接口字段差异 | 抽屉显示不全 | 宽松 DTO + 字段裁剪；失败不影响列表 |
| 真实节点无网站/计划任务数据 | 手工验收覆盖不足 | 假面板补样例；后续用其他节点补测 |
| P4 不做实时推送 | 数据非秒级 | 列表场景 TTL 30s + 手动刷新；如需再加 SignalR |
| 容器 ports/network 结构不稳定 | 展示异常 | 统一转字符串；缺失显示「—」 |

**已确认的决策（2026-11-16）**：

1. 数据库展示到**库级**（行 = 库，带引擎/实例列）；
2. 详情：行点击右侧抽屉，按需调详情接口；数据库用列表字段；
3. 数据量：每节点 200 条 / 合并 2000 条 / 每页 50 条；
4. 页面形态：`/resources/websites|apps|containers|databases|cronjobs` 五个路由；
5. 刷新：**后台定时刷新**（默认 60s，只刷新最近打开过的类型）+ 页面 10s `CacheOnly` 重读缓存 + 手动刷新；不做 SignalR 推送。

**实现时额外约束**：

- 后台刷新按类型串行执行（避免同时打满 5 类 × 全部节点）；单类刷新仍受 NodeTimeout/Budget 限制；
- 页面 10s 定时器只读缓存（`CacheOnly`），不触发网络；避免 TTL 30s 与后台 60s 叠加造成重复采集；
- REST `GET /api/resources/{kind}` 保持 EnsureFresh（测试/脚本友好）。

## 16. UI 调整：树状视图（2026-11-17）

用户反馈「资源应呈树状：节点 → 分类 → 资源，而不是平铺列表」，据此把 `/resources/{kind}` 页面从「跨节点合并表格」改为**三层层级树**：

- **节点层**：节点名 + 采集状态徽标（正常/部分成功/采集失败/已禁用/待刷新）+ 资源条数（含「共 N」与截断提示）+ 节点错误/警告摘要；
- **分类层**（可折叠；优先使用 1Panel 自定义分组）：
  - 网站：1Panel 网站分组（`POST /api/v2/groups/search`，`type=website`；默认分组/自定义分组名）。网站列表接口不带分组字段，loader 按 `websiteGroupId` 分组查询以获得归属；
  - 计划任务：1Panel 计划任务分组（`type=cronjob`，列表项自带 `groupID`）；
  - 应用 / 容器 / 数据库：1Panel v2.3.2 没有自定义分组，分别按应用类型、运行状态、数据库引擎归类；
  - 资源类型/状态（如网站的「反向代理」、计划任务的「备份网站」）只显示在资源叶节点行，**不再作为分类**；无分组信息时归入「未分类」。
- **资源叶节点**：名称 + 状态徽标 + 次要信息（协议/版本/镜像/实例/执行规则），点击仍然打开原详情抽屉。

实现要点：

- 数据仍复用 `IResourceQueryService`（一次 EnsureFresh 查询返回每个节点的完整 `NodeResourceResult.Rows`，树直接按节点分组，避免 N 次请求）；页面 10s `CacheOnly` 刷新与手动刷新行为不变；
- 搜索改为**客户端过滤**（名称/状态/属性值包含），不再使用分页（树展示每节点最多 200 条，标题栏显示「共 N」）；
- 新增 `ResourceTree.razor`（+ scoped CSS）、`ResourceCategoryClassifier.cs`；`ResourceTable.razor` 保留但不再使用；
- 测试：分类映射 10 项 + 页面树渲染 2 项（`tests/PanelFleet.IntegrationTests/ResourceTreeUiTests.cs`），全量 456 项测试通过。
