## 1. 目标与非目标

**目标**：打开 `/` 一屏看清所有节点的健康、负载、资源水位与资源计数，单节点失败不影响其它节点。

1. 复用 P2 的节点存储、DataProtection 密钥与登录会话；
2. 每节点**一次** HTTP 调用采集总览数据，全局并发受控；
3. 聚合引擎具备：并发上限、单节点超时、整轮预算、熔断、跳过/取消的明确语义；
4. 内存快照缓存 + TTL + Stale 标记；失败时保留上次成功数据并标注时间；
5. 通过 Blazor Server 的 SignalR 电路做**按节点增量渲染**，慢节点不阻塞其它卡片；
6. 汇总条：节点在线/降级/离线、网站/应用/数据库/计划任务总数、内存/磁盘总量与使用率、平均 CPU；
7. 节点卡片可操作：重试、打开 1Panel 面板（使用 P2 保存的安全入口）；
8. 对外提供只读 REST `GET /api/overview`，供测试、运维与后续客户端复用。

**非目标**（明确不做）：

- 历史曲线/时序存储、告警通知；
- 写操作、批量运维；
- 跨节点资源清单与详情（P4）；
- 持久化快照（重启后内存缓存清空，重新采集）；
- 独立 SignalR Hub（P3 复用 Blazor Server 电路，见 §7；如需非浏览器客户端实时推送，P4/P5 再评估）；
- 定时采集计入审计（避免审计噪音，见 §10）。

## 2. 数据来源与真实契约

### 2.1 端点选择：每节点一次调用

总览每节点只调用 **1 个**接口：

```
GET /api/v2/dashboard/base/all/all
```

该接口一次返回总览所需全部数据（2026-11-16 14:20 对 1Panel v2.3.2 实测，原始报文见 `docs/research/p3-api-probe.md`）：

- 主机信息：hostname / os（内核类别，如 `linux`）/ platform（发行版标识，如 `debian`）/ platformVersion / **prettyDistro**（展示名，如 `Debian GNU/Linux 13`）/ kernelVersion / kernelArch / **ipV4Addr** / cpuModelName / cpuCores / cpuLogicalCores / cpuMhz；
- 资源计数：websiteNumber / appInstalledNumber / databaseNumber / cronjobNumber（另有 agentNumber、quickJump[]，P3 不用）；
- 当前指标 `data.currentInfo`：cpuUsedPercent / cpuUsed / cpuTotal / cpuDetailedPercent / memoryUsed / memoryTotal / memoryUsedPercent / memoryAvailable / memoryFree / memoryShard / memoryCache / swapMemory* / load1 / load5 / load15 / loadUsagePercent / netBytesSent / netBytesRecv / ioReadBytes / ioWriteBytes / ioCount / ioReadTime / ioWriteTime / uptime / timeSinceUptime / runningTime / procs / shotTime / diskData[]（每个分区：path/type/device/total/free/used/usedPercent/inodes*）。

实测结论：

1. **`currentInfo` 内嵌在 `base/all/all` 中，每节点 1 次请求成立**，无需新增 HTTP 方法；
2. P3 只用 CPU/内存/负载/磁盘/uptime/shotTime；网络、IO、swap、GPU、inodes 等字段保留给 P4/P5；
3. `base/all/all` 不返回 1Panel 版本号；卡片的面板版本继续使用 P2 节点记录中的 `PanelVersion`（来自 `POST /settings/search`）；
4. 鉴权细节：`1Panel-Token` 请求头放的是 **HMAC 签名**（不是 API Key 原文），P1 客户端已如此实现；
5. `os` 是内核类别、`platform` 是发行版标识，UI 展示名优先 `prettyDistro`。

`ioOption=all`、`netOption=all` 表示不区分磁盘/网卡明细，由 P1 的 `PanelRoutes.DashboardBase("all","all")` 生成。

**为什么不用两个接口**：实测 `current/node` 的指标在 `base/all/all` 的 `currentInfo` 中已包含；两次调用会让请求量翻倍、并放大故障面。若某 1Panel 版本缺少 `currentInfo`，P3 **不追加第二次调用**，卡片显示「指标不可用（版本差异）」，资源计数与主机信息仍展示；等 P4 再做按能力探测的补充调用。

> 探测原始 JSON、字段类型表与示例值见 `docs/research/p3-api-probe.md`；字段名以该探测结果为准（探测结果与本设计冲突时，先修文档再实现）。

### 2.2 现有 DTO 复用与扩展

复用 P1 已存在的宽松 DTO（`[JsonExtensionData]` 已保留未知字段，字段缺失不抛异常）：

| DTO | 用途 | 需要的字段 | 处理 |
|---|---|---|---|
| `DashboardBaseDto` | 主数据源 | 全部主机信息 + 4 个计数 + `CurrentInfo` | 复用；**补 `PrettyDistro`、`IpV4Addr` 两个属性**（纯追加） |
| `DashboardCurrentDto` | `currentInfo` | CPU/内存/负载/网络/uptime/diskData | 直接复用 |
| `DiskInfoDto` | 磁盘明细 | device/path/type/total/used/free/usedPercent | 直接复用 |

**客户端改动**：只给 `DashboardBaseDto` 追加 `PrettyDistro`、`IpV4Addr` 两个可空字符串属性（真实报文有、现有 DTO 未映射；`[JsonExtensionData]` 已兜底，但显式映射便于展示与测试）。不新增 DTO，不新增 HTTP 方法；契约测试补一条「真实完整报文」用例。

**映射规则**（`OverviewMapper`，纯函数、可单测）：

1. 缺失或 `null` 的字符串保持 `null`；
2. 百分比限定在 `[0,100]`；CPU/内存百分比缺失时为 `null`（不显示 0% 假数据）；
3. 字节数 `long`；`memoryUsed/memoryTotal` 缺失时为 `null`；
4. `diskData` 为空/缺失 → `Disks=[]`、`MaxDiskUsedPercent=null`；
5. 磁盘汇总：`DiskTotalBytes=Σdisk.total`、`DiskUsedBytes=Σdisk.used`；**卡片展示使用率最高的分区**（`MaxDiskUsedPercent` + `MaxDiskPath`，实测本机 `/` 60.3%、`/data/Routing` 94.7% → 显示后者），汇总条用加权使用率；inodes 字段忽略；
6. `SampledAt` 取 `shotTime`（UTC ISO-8601，如 `2026-11-16T06:00:21.486069412Z`）；缺失时用采集完成时间；
7. 计数缺失按 0（1Panel 必返回计数；0 视为真实 0）；
8. **展示名**：`prettyDistro` → `platform + " " + platformVersion` → `platform` → `os` → 节点名；
9. **CPU 核数**：`cpuLogicalCores > 0` 时展示它，否则 `cpuCores`（实测 LXC：`cpuCores=8`、`cpuLogicalCores=2`，展示「2 核」，含义为容器可见核数）；
10. `loadUsagePercent` 可能 >100（实测 132），P3 不使用；负载直接展示 load1/5/15 原始值；
11. `runningTime`/`timeSinceUptime` 不使用，运行时长由 `uptime` 秒数计算。

### 2.3 请求参数与鉴权

- 完全复用 `IPanelClientFactory` + `ApiKeySigningHandler`（HMAC/MD5 Auto、时钟偏差重试、gzip、HTML 响应识别）。
- 节点 `BaseUrl` 只填 API 根地址；`SecurityEntrance` 不参与任何 API 路径（P2 约定）。
- 客户端超时：`OnePanel:RequestTimeout`（默认 8s）是单次 HTTP 兜底；聚合层另有 6s 单节点超时（更早触发）。6s 先触发时 `PanelClient` 捕获外部取消返回 `PanelErrorKind.Canceled`，由 FanoutEngine 统一改标为 `TimedOut`（文案「节点响应超时（6 秒）」），**不重试、不二次报警**；8s 兜底只在未设置聚合超时的调用（如 P2 连接测试）生效。

|---|---|

| `AttemptedAt is null` | `Pending` |
| `Error is not null && Metrics is null` | `Failed` |

## 4. 聚合调用引擎（FanoutEngine）

> 通用、与总览解耦；P4 资源清单直接复用。位于 `PanelFleet.Application/Overview/FanoutEngine.cs`。

### 4.1 接口

```csharp
public sealed record FanoutTarget<T>(NodeId NodeId, string NodeName, Func<CancellationToken, Task<T>> Call);

public enum FanoutStatus { Success, Failed, TimedOut, BudgetExceeded, CircuitSkipped }

public sealed record FanoutResult<T>(
    NodeId NodeId,
    FanoutStatus Status,
    T? Data,
    PanelError? Error,
    TimeSpan Elapsed,
    DateTimeOffset CompletedAt);

public sealed class FanoutOptions
{
    public int MaxConcurrency { get; init; } = 6;
    public TimeSpan PerTargetTimeout { get; init; } = TimeSpan.FromSeconds(6);
    public TimeSpan Budget { get; init; } = TimeSpan.FromSeconds(10);
    public int ChannelCapacity { get; init; } = 256;
}

public interface IFanoutEngine
{
    IAsyncEnumerable<FanoutResult<T>> RunAsync<T>(
        IReadOnlyList<FanoutTarget<T>> targets,
        FanoutOptions options,
        CancellationToken cancellationToken);
}
```

### 4.2 行为约束

| 规则 | 约束 |
|---|---|
| 并发 | `Parallel.ForEachAsync`，`MaxDegreeOfParallelism = MaxConcurrency`；任意时刻运行中的 target 数 ≤ MaxConcurrency |
| 单节点超时 | 每 target 一个 linked CTS，`CancelAfter(PerTargetTimeout)`；超时 → `Status=TimedOut`，不影响其它 target |
| 整轮预算 | 全局 linked CTS `CancelAfter(Budget)`；预算到点 → 取消在途 target，`Status=BudgetExceeded`；已成功的不回滚 |
| **结果完整性（硬约束）** | 除调用方取消外，**每个 target 恰好产出 1 条结果**：预算耗尽时未开始/未完成的 target 必须补 `BudgetExceeded`；实现为 producer 记录已完成 NodeId 集合，`Parallel.ForEachAsync` 结束后补齐差额再关闭 channel，避免 UI 永远停在 Pending |
| 区分取消源 | 先看调用方 token（停止）→ 结束枚举；再看预算；最后看单节点超时 |
| 流式产出 | 通过 `Channel<FanoutResult<T>>`（bounded，容量 `ChannelCapacity`，满则等待）**按完成顺序**产出；慢节点不阻塞快节点 |
| 异常 | target 抛非取消异常 → `Status=Failed`，`PanelError(Protocol, ...)`，不向调用方抛出；`OperationCanceledException` 由引擎分类 |
| 调用方取消 | 枚举抛 `OperationCanceledException`（标准 async enumerable 语义）；不产生 Completed 事件 |
| 输入校验 | 空 targets → 立即完成；重复 NodeId → `ArgumentException`（编程错误） |
| 结果内容 | `Elapsed` 为单 target 墙钟；`CompletedAt` 为完成时刻；`Error` 仅 Failed 时有值 |

`CircuitSkipped` 由总览服务在调用引擎**之前**生成（引擎不知道熔断），保证结果集合完整。

## 5. 熔断（NodeCircuitBreaker）

> 进程内、按 NodeId；目标：持续故障的节点不每 30s 消耗 6s 超时预算，同时用户可手动强制重试。

```csharp
public enum CircuitState { Closed, Open, HalfOpen }

public sealed record CircuitStatus(CircuitState State, int ConsecutiveFailures, DateTimeOffset? OpenUntil);

public interface INodeCircuitBreaker
{
    CircuitStatus GetStatus(NodeId nodeId, DateTimeOffset now);
    bool TryEnter(NodeId nodeId, DateTimeOffset now, bool force); // false = 本轮跳过
    void RecordSuccess(NodeId nodeId);
    void RecordFailure(NodeId nodeId, PanelErrorKind kind, DateTimeOffset now);
}
```

| 规则 | 约束 |
|---|---|
| 触发阈值 | 连续失败 `FailureThreshold`（默认 3）次 |
| 打开时长 | `BreakSeconds`（默认 30s）；期间 `TryEnter=false`，快照 `CircuitOpen=true` |
| 半开 | 到期后第一个 `TryEnter` 放行（同时只允许 1 个探针），成功 → Closed，失败 → 重新 Open `BreakSeconds` |
| 计入失败的 Kind | `Network / Tls / Timeout / Protocol / PanelServerError` |
| 不计入失败的 Kind | `Unauthorized / Forbidden / NotFound / Unsupported / Validation / Canceled`（配置类错误需用户立刻看到，不熔断） |
| 手动重试 | `force=true` 绕过 Open 直接调用；结果照常记录（成功即 Closed；失败重新 Open） |
| 成功 | 任何 `Success` 结果 → `RecordSuccess` 清零 |
| 并发 | `ConcurrentDictionary<NodeId, Entry>`，Entry 内 `lock`；无全局锁 |
| 持久化 | 不持久化，重启清零 |

**与健康巡检的关系**：P2 `NodeHealthMonitor` 仍独立巡检并写数据库健康（60s/次）；熔断只作用于 P3 聚合调用，二者互不影响。总览不写数据库（只读原则，避免与巡检写竞争）。

## 6. 快照缓存与刷新协调

### 6.1 缓存（`IOverviewCache`，单例）

```csharp
public sealed record NodeOverviewData(
    NodeMetrics? Metrics,
    PanelError? Error,
    DateTimeOffset? FetchedAt,
    DateTimeOffset? AttemptedAt,
    TimeSpan LastLatency,
    bool LastAttemptSucceeded);

public interface IOverviewCache
{
    CacheSnapshot GetSnapshot();                             // 不可变拷贝，线程安全
    bool ApplyNode(NodeId nodeId, NodeOverviewData data);    // 时序保护：AttemptedAt 不新于现有值时拒绝，返回 false
    void Prune(IReadOnlySet<NodeId> validNodeIds);           // 清理已删除节点
    void SetRefreshing(bool refreshing);
    void MarkRunCompleted(TimeSpan elapsed);                 // 记录最近一轮耗时
}

public sealed record CacheSnapshot(
    IReadOnlyDictionary<NodeId, NodeOverviewData> Nodes,
    bool IsRefreshing,
    DateTimeOffset? LastCompletedAt,
    TimeSpan? LastRunElapsed,
    long Generation);
```

- 存储：`ConcurrentDictionary` + `volatile` 状态字段；`GetSnapshot()` 返回不可变字典拷贝（≤20 节点，成本可忽略）；
- **写入时序保护（CAS）**：`ApplyNode` 只在 `data.AttemptedAt` 晚于已存 `AttemptedAt` 时生效，返回值表达是否被采纳；这样「整轮刷新」与「单节点重试」并行时，**旧结果不会覆盖新结果**；
- `Prune` 在每轮整轮刷新结束时调用，移除已删除节点的缓存条目；
- **只缓存动态数据**；节点名称/地址/分组/启用状态每次从数据库读取（节点增删改立即反映，无需等下一轮）；
- 重启清空；无持久化。

### 6.2 刷新队列与后台服务

```
UI/API ──RequestFull()──▶ IOverviewRefreshQueue (Channel, 单例，仅整轮刷新)
                               │
OverviewRefreshHost (BackgroundService) ◀────┘ 串行消费整轮刷新
        │
        └─ IServiceScopeFactory.CreateScope() ─▶ IOverviewService (scoped)

UI/API ──RequestNode(id)──▶ IOverviewService.RefreshNodeAsync(id, force:true)
                              （直接执行、不排队；按节点 SemaphoreSlim 串行）
```

| 组件 | 职责 |
|---|---|
| `IOverviewRefreshQueue`（Application 单例） | 只接收整轮刷新请求：`RequestFull()` 合并式入队（已有待处理整轮则忽略）；`ReadAllAsync` 供宿主消费 |
| `OverviewRefreshHost`（Web `BackgroundService`） | 启动延迟 3s 后请求一轮；之后每 `RefreshIntervalSeconds` 请求一轮；串行处理队列项；每项创建 scope 调用 `IOverviewService.RefreshAllAsync`；用应用停止 token 取消，不受浏览器断线影响 |
| `IOverviewService`（Application scoped） | `GetSnapshotAsync` / `RefreshAllAsync`（经队列）/ `RefreshNodeAsync`（直通） |

约束：

- **整轮刷新串行**（同一时刻最多 1 个整轮），避免总览整体对同一节点重复请求；
- **单节点刷新直通**：不经过队列，直接调用 `RefreshNodeAsync(id, force:true)`；与整轮可并行，靠「每节点 `SemaphoreSlim(1,1)` + 缓存 `ApplyNode` 时序保护」保证同节点不并发、旧结果不覆盖新结果；
- 队列容量默认 64；`RequestFull` 用待处理标志去重；
- 后台刷新间隔 `0` 或负数 = 禁用自动刷新（只保留手动/按需），默认 30s；
- 页面打开时：先读缓存（快），若缓存空或过期（> `CacheTtlSeconds`）再 `RequestFull()`；
- 手动刷新按钮 → `RequestFull()`；卡片「重试」→ 直接 `await RefreshNodeAsync(id, force:true)`，按钮 busy，返回即更新；
- **不做**「重试排队等整轮」：那会让最坏等待变成 整轮 10s + 单节点 6s，体验不可接受。

### 6.3 TTL / Stale 语义

| 概念 | 默认 | 含义 |
|---|---|---|
| `CacheTtlSeconds` | 25 | 页面打开时缓存「足够新」的阈值；超过则请求刷新 |
| `RefreshIntervalSeconds` | 30 | 后台整轮刷新间隔（自动刷新） |
| `StaleAfterSeconds` | 90 | 指标超过该年龄即标记 `IsStale`（即使最近一次调用失败前保留的数据也一样） |

- 失败时：`Metrics` 保留、`Error` 记录、`AttemptedAt` 更新；卡片显示「缓存数据 · X 分钟前」+ 错误；
- 从未成功过：`Metrics=null`、State=Failed；
- 熔断跳过：同样更新 `AttemptedAt` + `Error(PanelErrorKind.Timeout, "熔断中，{剩余}s 后自动重试")`？—— **不**：跳过不视为失败尝试，仅 `CircuitOpen=true` 标记，保留原 `AttemptedAt`；UI 显示「熔断中 · 剩余 Ns」+ 强制重试按钮。

### 6.4 采集流程（`RefreshAllAsync`）

1. `nodes = INodeService.ListAsync()`（含禁用；排序规则见 §3.2）；
2. `cache.SetRefreshing(true)`；`broadcaster.Publish(RunStarted(enabledCount, now))`；
3. 对每个禁用节点：生成 `Disabled` 快照（不发请求），缓存 `AttemptedAt=null`；
4. 对熔断 Open 的节点：生成 `Stale/Failed` 快照（`CircuitOpen=true`），不发请求，不更新缓存数据；
5. 其余节点构造 `FanoutTarget`：
   - 解密 API Key（`INodeSecretProtector`）；
   - `NodeDescriptor(Id, Name, BaseUrl, ApiKey, AuthMode, TlsPolicy, ClockOffset)`（从 `NodeRecord` 读取 `ClockOffsetSeconds`，无需改公共 summary DTO）；
   - `Call = ct => client.GetDashboardBaseAsync("all","all", ct)`，`using` 客户端；
   - `ct` 由引擎给到（单节点超时）；
6. `await foreach result in fanout.RunAsync(targets, options, stoppingToken)`：
   - 成功 → 映射 `NodeMetrics`，`RecordSuccess`，缓存 `LastAttemptSucceeded=true`；
   - `TimedOut` → `PanelError(Timeout, "[名称] 节点响应超时（6 秒）")`，`RecordFailure(Timeout)`；
   - `BudgetExceeded` → `PanelError(Timeout, "本轮总预算 10 秒耗尽，稍后自动重试")`；**不记熔断**（全局预算不是单节点的错，避免误开熔断），保留缓存并标注错误；
   - `Failed` → 保留 PanelError，`RecordFailure(kind)`；
   - 任一失败都保留旧 Metrics；
   - `ApplyNode` + `Publish(NodeUpdated)`；
7. `cache.Prune(本轮节点 Id 集合)`；生成 `FleetOverview`（`GetSnapshotAsync` 同源逻辑）→ `MarkRunCompleted(elapsed)` → `Publish(RunCompleted)`；`SetRefreshing(false)`；记录 Information 日志：节点数/成功/失败/跳过/耗时；
8. 步骤 6 中每完成一个节点即时 `Publish(NodeUpdated)`，UI 用 `RunStarted` 的 NodeCount 与已推送数量计算「采集中 n/N」进度，不额外发进度事件。

异常兜底：刷新整体异常（DB、未捕获）→ 记录 Error 日志、`SetRefreshing(false)`、`Publish(RunCompleted(当前缓存))`，不向宿主抛出（宿主继续下一轮）。

### 6.5 单节点刷新流程（`RefreshNodeAsync`，不走队列）

1. 从数据库读取该节点（不存在 → 抛出 `NodeNotFoundException`；禁用 → 返回 `Disabled` 快照，不发请求）；
2. 熔断 Open 且 `force=false` → 返回带 `CircuitOpen` 的当前快照，不发请求；`force=true` 直接发请求（成功后关闭熔断）；
3. 进入该节点的 `SemaphoreSlim(1,1)`（按 NodeId 的 gate，单例持有），保证同节点同时只有 1 个采集，且**不阻塞其它节点**；
4. 构造 `NodeDescriptor`，调用 `GetDashboardBaseAsync("all","all")`，超时 6s；单 target 直接调用，**不占整轮预算**；
5. 映射/错误分类 → `cache.ApplyNode`（CAS，返回是否采纳）→ `broadcaster.Publish(NodeUpdated)` → 返回最新 `NodeOverviewSnapshot`；
6. 不发布 `RunStarted/RunCompleted`（避免干扰整轮进度状态）；REST 端点同步等待并返回 200；Blazor「重试」按钮直接 await（UI 线程不阻塞，按钮 busy）。

## 7. 增量推送与前端更新

**方案：复用 Blazor Server 自身的 SignalR 电路，不额外建 Hub。**

- `IOverviewBroadcaster`（单例）：每个订阅者一个 `Channel<OverviewEvent>`（bounded 256，`DropOldest`），`Publish` 时写入所有订阅者；订阅者释放即移除；
- **订阅时机（关键）**：`Home.razor` 的 `OnInitializedAsync` **只** `GetSnapshotAsync()` 渲染；在 `OnAfterRenderAsync(firstRender)` 且 `RendererInfo.IsInteractive == true` 时才订阅并启动消费循环。**禁止在 `OnInitializedAsync` 订阅**：Blazor Server 预渲染会执行一次初始化，该实例不是交互实例，会导致重复订阅与后台循环泄漏；
- 消费循环：`await foreach (var e in subscription.Events)` → 更新本地字典 → `await InvokeAsync(StateHasChanged)`；循环内捕获异常（记录 Error 日志后停止消费，避免拖垮电路）；
- **相对时间刷新**：页面持有 10s `PeriodicTimer`，到点只 `InvokeAsync(StateHasChanged)` 刷新「X 秒前」文本，不重新请求数据；
- 断线重连：Blazor 电路重连后组件状态保留；页面重新加载则重新读缓存 + 订阅；
- 因此「SignalR 增量推送 + 卡片独立更新」由 Blazor 电路天然满足，不额外建 Hub；REST `GET /api/overview` 提供同一份快照，供非 Blazor 场景与自动化测试使用；
- 若未来需要非浏览器客户端实时推送，再单独加 Hub（P4/P5 评估），预期复用同一 `IOverviewBroadcaster`。

**前端合并规则**：

- `RunStarted` → `IsRefreshing=true`、`CompletedCount=0`，刷新按钮进入忙碌态并显示「采集中 0/N」；
- `NodeUpdated` → 按 `NodeId` 替换对应快照（幂等），`CompletedCount++`；
- `RunCompleted` → 用完整快照整体替换（防止漏事件导致的不一致），`IsRefreshing=false`，更新汇总条、「最近更新」与「本轮耗时/成功失败数」；
- 页面 `DisposeAsync` 时取消消费循环与 10s 定时器并释放订阅。

## 9. REST API

均要求 `Admin` 策略（与 P2 一致）；修改类操作要求 `X-CSRF-TOKEN`。

| 方法 | 路径 | 说明 | 成功 | 错误 |
|---|---|---|---|---|
| GET | `/api/overview` | 当前快照（合并数据库节点信息；无缓存时返回 Pending 卡片） | 200 `FleetOverview` | 401/403 |
| POST | `/api/overview/refresh` | 请求整轮刷新（合并入队，不等待） | 202 `{ accepted: true }` | 400 CSRF/401/403 |
| POST | `/api/overview/nodes/{id}/refresh` | 单节点强制刷新（绕过熔断；**同步等待**，最长 单节点超时+2s） | 200 `NodeOverviewSnapshot` | 400/401/403/404 |

- 整轮刷新不做 `?wait=true`；自动化测试直接调用 `IOverviewService.RefreshAllAsync` 或轮询 GET；
- 单节点刷新同步返回，便于脚本/排障；Blazor 页面「重试」同样直接 await（UI 线程不阻塞，按钮 busy）；
- 手动刷新频率保护：整轮请求合并；单节点靠每节点 gate 串行，重复请求最多 1 个在跑、后到者等待（≤6s）后返回最新快照；
- `GET /api/overview` 中禁用节点 `State=Disabled`；从未采集过 `Pending`。

## 10. 授权、审计与安全

- **授权**：全部端点与页面要求已登录 + `Admin` 策略（P2 现状；`ReadOnlyRoles` 仍不启用）。P3 只读，无新增权限模型；
- **审计**：刷新是高频只读行为，**不写审计**；登录/节点变更仍由 P2 审计覆盖。刷新结果写结构化日志：
  - Information：每轮一条（节点/成功/失败/跳过/耗时）；
  - Warning：单节点失败（按节点+错误类型；熔断打开/关闭各一条）；
  - Debug：单节点成功；
- **密钥**：快照/事件/日志/审计均不含 API Key；解密仅存在于构造 `NodeDescriptor` 的瞬时；
- **只读**：不写数据库（除读取节点）；不调用 1Panel 写接口；
- **出站保护**：整轮全局并发 ≤ MaxConcurrency；整轮刷新串行 + 每节点 `SemaphoreSlim` gate + 单节点直通，保证同一节点不会并发请求；整轮预算 10s 限制最坏耗时；熔断降低持续故障节点的请求频率；
- **缓存**：仅进程内存，含主机名/OS/资源用量等非敏感信息，重启清空。

## 11. 配置

| 配置键 | 默认值 | 范围 | 说明 |
|---|---|---|---|
| `Overview:RefreshIntervalSeconds` | 30 | `0`（或负数）=禁用；合法 10..3600；1..9 **启动失败** | 后台整轮刷新间隔 |
| `Overview:CacheTtlSeconds` | 25 | 5..600 | 页面打开时缓存新鲜阈值 |
| `Overview:StaleAfterSeconds` | 90 | 30..3600 | 指标过期标记阈值 |
| `Overview:MaxConcurrency` | 6 | 1..16 | 聚合并发上限 |
| `Overview:NodeTimeoutSeconds` | 6 | 2..30 | 单节点超时 |
| `Overview:BudgetSeconds` | 10 | 3..60 | 整轮预算 |
| `Overview:Circuit:FailureThreshold` | 3 | 1..10 | 熔断阈值 |
| `Overview:Circuit:BreakSeconds` | 30 | 5..600 | 熔断持续时长 |

- 配置校验（启动时 fail-closed）：除 `RefreshIntervalSeconds` 允许 0/负数表示禁用外，**任何数值越界都直接启动失败**并抛出明确异常（与 OIDC 一致）；不做静默 clamp，避免“配置写错却看起来正常”；
- `RefreshIntervalSeconds ∈ 1..9` 视为非法（防止误配成 5 秒把面板打爆）；禁用自动刷新必须显式写 `0`；
- 集成测试设置 `Overview__RefreshIntervalSeconds=3600` 避免后台干扰；手工验收使用默认 30s；
- 负载估算：N 个节点 → 每 30s N 次请求（20 节点 = 40 次/分钟），对 1Panel 负载很小；若节点更多可调大间隔。

## 17. 风险与待确认问题

| 风险/问题 | 影响 | 对策/待确认 |
|---|---|---|
| 真实 `base/all/all` 字段与预期不同 | 映射错误/指标缺失 | 已对真实节点探测并固化完整报文（`docs/research/p3-api-probe.md`），契约测试用真实报文防漂移；字段变更时以探测为准先修文档 |
| 每节点只调 1 接口 | 某些 1Panel 版本 `currentInfo` 缺失 | P3 显示「指标不可用」；P4 按能力探测补充 `current/node` |
| 20+ 节点 × 30s 轮询 | 面板压力/预算耗尽 | 默认并发 6 + 预算 10s + 熔断；节点多时调大 `RefreshIntervalSeconds`，文档注明 |
| 熔断掩盖短暂网络抖动 | 用户看到「熔断中」 | 30s 后自动半开；手动重试强制绕过 |
| Blazor 电路断开/重连 | 增量更新中断 | 重连后组件重新渲染并读缓存；`RunCompleted` 全量覆盖兜底 |
| 反向代理部署下「打开面板」地址 | 外网/HTTPS 跳转错误 | 使用节点 `BaseUrl`（已含用户填写的外部地址）；P2 已要求地址与入口分离 |
| 汇总磁盘/内存跨节点求和 | 近似值（同一物理盘多节点重复） | UI 标注「跨节点合计」；P3 不做去重 |
| 总览刷新不写审计 | 无刷新历史可追溯 | 设计选择（避免噪音）；如需追溯可后续加采样审计 |
| DataProtection 应用名/密钥环不一致 | 节点 API Key 密文无法解密 | 已显式 `SetApplicationName("PanelFleet")` 并持久化密钥环；备份 `data` 目录可保留密钥，换机需重新录入节点 Key |
| Blazor 预渲染导致重复订阅 | 内存/事件翻倍 | 订阅只在 `OnAfterRenderAsync(firstRender)` 且 `RendererInfo.IsInteractive` 时进行（§7） |
| 单节点重试与整轮刷新并行 | 旧结果覆盖新结果 | 每节点 gate + 缓存 `ApplyNode` 按 `AttemptedAt` CAS（§6.1/§6.5） |
| 相对时间不自动变化 | 显示「3 秒前」静止 | 页面 10s 定时器只刷新时间文本（§7） |
| 每轮新建 HttpClient（无连接复用） | 延迟/握手开销 | 当前量级可接受；P5 做客户端池化（见下） |

**已确认的决策（2026-11-16）**：

1. 增量推送复用 Blazor Server 电路，不建独立 Hub；
2. 每节点只调 1 次 `base/all/all`；
3. 默认 30s 自动刷新 + 手动刷新；固定排序、不做筛选；
4. P3 实现「打开面板」按钮（使用 `SecurityEntrance`）；
5. 刷新不写审计，只写结构化日志。

**已采纳的增强（A/B/C/D）**：

- A：单节点重试直通 + 每节点 gate + 缓存写入 CAS；Fanout 结果完整性（每 target 恰好 1 条）；两级超时关系明确；
- B：预渲染订阅生命周期、10s 相对时间定时器、消费循环异常停止；
- C：汇总条进度/耗时/成功失败数、磁盘最高使用率节点、错误前缀裁剪、缓存 prune；
- D：配置 fail-closed 边界、`TimeProvider` 注入测试、健康双来源 tooltip、打开面板 URL 规则、合计覆盖口径标注。

**明确延后（E，记入后续阶段）**：

- 客户端池化/连接复用（20 节点约 40 请求/分钟，暂可接受）→ P5；
- 整轮 REST 同步等待接口（按需再加）；
- 健康筛选/异常优先排序、网络速率/swap/进程数展示 → P4；
- 巡检与总览请求合并（巡检复用总览结果）→ P5；
- 历史曲线/告警 → P5+。
